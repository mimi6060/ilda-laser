## Contexte
Chaque nouvelle fonction (cues, LFO, MIDI, calques, timeline) peut contourner une protection par accident. Il faut des tests qui vérifient les invariants de sécurité sur des entrées aléatoires, et qui tournent à chaque `cargo test`.

## À faire
- Tests de propriétés (`proptest`, dev-dependency) sur le pipeline complet (générateur → modificateurs → calibration → T-003 → T-254 → T-256 → T-262 → porte T-250), avec une sortie factice :
  1. Désarmé ou arrêt d'urgence actif ⇒ aucun point allumé envoyé.
  2. Aucune couleur envoyée > plafond de la sortie (global et par couleur).
  3. Aucun point allumé dans une zone Blank (y compris sur les segments qui la traversent).
  4. Mode extérieur ⇒ aucun point allumé hors secteurs ; « Ciel coupé » ⇒ aucun point d'élévation > 0 (quand T-262 existe, test ignoré sinon).
  5. Coordonnées envoyées toujours dans -1..1.
  6. Aucune suite de messages MIDI/API (générée) ne fait passer `armed` à vrai sans une demande d'armement explicite autorisée.
- Scénarios e2e (Playwright, aperçu, `--data-dir` temporaire) : perte de battement (T-252), arrêt d'urgence verrouillé (T-251), refus d'armement avec liste de verrous.
- Documenter dans `studio/e2e/README` (ou le README de tests existant) comment ajouter un invariant quand une nouvelle protection arrive.
